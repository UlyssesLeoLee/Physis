## 2. 文档目的

本文档回答以下问题：

- GVPE 的工程流程**如何**对齐业界（日本 PM/SE 圈）通用的 150 步基线？
- 27 份现有设计文档**分别对应** 150 步中的哪些产出物？
- 哪些工作流步骤是 GVPE 作为**库产品**（非业务系统）天然 **N/A** 的？
- 哪些步骤**已经覆盖**（有文档），哪些**待补**（有流程但无文档）？
- 实施期 / 维护期的 PR 流程、Code Review、变更管理应**如何**与本文件对齐？

## 3. 适用范围

- **适用阶段**：MVP 实施启动**前**冻结，作为 PR / Code Review / 变更管理的流程索引；
- **适用读者**：所有 GVPE 贡献者、Code Reviewer、Release Manager、维护者；
- **强制力**：标记为 **📋 流程定义中**的步骤，在实施期必须有对应 PR / 流程落地；标记为 **⚠️ 待补**的步骤必须在 MVP 启动前补齐对应文档或登记为 `QA-B-*` 类风险（见 `GVPE-DOC-27`）；
- **不适用**：GVPE 作为**库产品**（非业务系统），部分 PMBOK-style 流程（本番环境、运维、UAT 业务部门）天然 N/A；本文件显式标记为 ❌，不做补救。

## 4. 术语定义

| 术语 | 释义 |
|---|---|
| 150 步工程流程 | 日本 PM/SE 圈通用的工程流程分解，由 16 个阶段、共 150 个步骤组成；本文件采纳为 GVPE 流程基线。 |
| 阶段（フェーズ） | 流程中的一级分类，本文件共识别 16 个阶段。 |
| 略称 | 业界通用的步骤缩写（如 UR = User Requirements）。 |
| GVPE 对应文档 | 该步骤产出物对应的 `GVPE-DOC-NN`；如多项则用 `,` 分隔。 |
| 状态 | 四类状态之一（见 §5）。 |
| 覆盖率 | 已覆盖步骤数 / 适用步骤数（不含 N/A）。 |
| 缺口（Gap） | 应有但尚未覆盖的步骤。 |
| 库产品（library product） | GVPE 作为可嵌入库（`cdylib` / `staticlib` / `rlib`），非业务系统；其工程流程在客户业务侧不涉及的部分为 N/A。 |

## 11. 流程定义（针对 📋 状态步骤）

> 本节针对标记为 📋 的步骤，给出 GVPE 工程团队应遵循的具体流程。每条流程均不依赖外部文档，**在本文件中**完整定义。

### 11.1 项目启动（05）

- **触发**：本文件 + 27 号 QA 表经审批后；
- **动作**：建立 git 主分支策略（`main` / `develop` / `feature/*` / `release/*` / `hotfix/*`）；建立 GitHub 仓库设置（branch protection、required reviewers、CI gating）；建立团队沟通渠道；
- **产出**：仓库初始化、CI 首次绿、`docs/00` ~ `docs/28` 已落盘（已完成）。

### 11.2 要求评审（20）

- **触发**：MVP 启动前 / 每次大版本需求变更前；
- **评审人**：架构师 + 至少 2 名核心 crate 维护者；
- **流程**：对照 `GVPE-DOC-01`（需求规约）逐条检查 ID 完整性（FR / NFR / GPH / VEC / PERF / LIC / PROHIBIT / NG / AC）、可验证性、跨文档一致性；对照 `GVPE-DOC-27`（QA 登记）检查 Blocker 是否全部 Closed；
- **产出**：评审纪要（GitHub PR 评论 + commit message），签字后进入 §11.3。

### 11.3 要求批准 / 基线化（21）

- **触发**：§11.2 评审通过；
- **动作**：在 `GVPE-DOC-01` §1 修订历史增加 v0.X 条目；为基线打 git tag（如 `v0.1-baseline`）；
- **不可逆**：基线一经建立，下游文档的引用必须以基线为准；变更需走 §11.32 变更管理。

### 11.4 基本设计评审（41）

- **触发**：每次基本设计文档（22 ~ 40 步对应文档）变更后 / MVP 启动前；
- **评审人**：架构师 + 对应模块负责人；
- **流程**：检查 `GVPE-DOC-04` ~ `16` 的 §审批 签字位是否齐全；检查 `GVPE-DOC-26`（技术选型）与 `GVPE-DOC-27`（QA 登记）是否对齐；
- **产出**：评审纪要 + 签字。

### 11.5 详细设计评审（52）

- **触发**：每次详细设计文档（42 ~ 51 步对应文档）变更后 / 实施启动前；
- **评审人**：架构师 + 对应 crate 实现者；
- **流程**：检查 `GVPE-DOC-17` ~ `25` 的 §审批；检查 `GVPE-DOC-26` §18 选型是否在详细设计中正确应用；检查 `GVPE-DOC-27` §9 中对应 I / T 类 QA 项是否在设计中得到回应；
- **产出**：评审纪要 + 签字。

### 11.6 编码（54）

- **入口条件**：对应模块的 §52 DD Review 通过；
- **行为规范**：
  - 一个 PR = 一个最小可评审单元（单一关注点）；
  - PR 标题：`[crate-name] short description`；
  - PR 描述：动机、改动点、关联 ID（`GVPE-FR-XXX` / `GVPE-NFR-XXX` / `GVPE-PROHIBIT-XX` / `QA-X-NN`）、影响范围、是否破坏 ABI；
  - 任何 `unsafe` 必须有 `// SAFETY:` 注释；
  - 热路径无 `String` / `Vec` / `HashMap`（除非在冷路径或经设计评审特批）；
  - 关联 `GVPE-DOC-26` §18 选型：禁止使用 §18.13 拒绝清单中的任何库。

### 11.7 代码评审 / 单测评审（56 / 61）

- **触发**：任何 PR 提交；
- **最低 reviewer 数**：1（普通修改）/ 2（涉及 `unsafe` / 公开 API 形状 / `Cargo.toml` 依赖变更 / 任何 `GVPE-PROHIBIT-*` 触及点）；
- **Reviewer checklist**（PR 模板化）：
  - [ ] 是否符合 `GVPE-DOC-26` 选型？
  - [ ] 是否触及 `GVPE-DOC-27` 中对应 Blocker / High QA 项？
  - [ ] 是否新增 / 修改了任何 `unsafe`？是否有 `// SAFETY:` 注释？
  - [ ] 是否引入了 `String` / `Vec` / `HashMap` 到热路径？
  - [ ] 单元测试是否覆盖？是否触及 `GVPE-FR-001` feature-gate 验证？
  - [ ] 是否破坏 ABI（任何 `#[repr(C)]` 类型字段变化）？
  - [ ] 是否更新了对应设计文档（doc drift 风险）？
- **结论**：approve / request changes / comment。

### 11.8 单元测试实施（62）

- **入口条件**：PR 中包含 `cargo test` 通过的 CI 状态；
- **行为规范**：
  - 每个新公共 API 至少 1 个 happy path + 1 个 error path 测试；
  - 每个 `unsafe` 块至少 1 个 miri 验证（CI 中 `cargo +nightly miri test`，对核心 unsafe crate）；
  - 接触 / 求解器相关 crate 必须有对照实现测试（参考 Bullet / PhysX 行为，不嵌入第三方库）；
  - 性能关键 crate 必须有 criterion bench（CI 不强制跑，但 PR 应提供本地 bench 结果）。

### 11.9 不具合修正（63）

- **入口条件**：bug report（GitHub Issue / 集成方反馈 / 自身 fuzz 发现）；
- **行为规范**：
  - bug 进入 `GVPE-DOC-27` §9（如属实施前已知）或 GitHub Issues（实施期发现）；
  - 修正 PR 引用 bug 编号；
  - 修正后需新增**回归测试**（防止回归）；
  - 影响 ABI / 公开 API 的 bug 修正需走 §11.32 变更管理。

### 11.10 再试验（64）

- **入口条件**：bug 修正后；
- **行为规范**：
  - 重新跑全部 unit test（不仅是修正相关测试）；
  - 重新跑相关 criterion bench（性能 bug）；
  - 重新跑 miri（如触及 unsafe）；
  - 重新跑 determinism harness（如触及求解路径或热路径）。

### 11.11 单元测试完成批准（65）

- **触发**：每个 crate 的 MVP 功能完成时；
- **批准人**：crate 维护者 + 1 名架构师；
- **产出**：crate 标记为 `feature-complete`，进入下一阶段。

### 11.12 内部集成测试（69）

- **入口条件**：同 crate 多模块单元测试完成；
- **测试重点**：模块间接口契约、共享状态、生命周期；
- **工具**：crate 内部 `tests/` 目录下的集成测试；
- **通过标准**：所有测试通过 + clippy 干净 + 无 miri 警告。

### 11.13 外部集成测试（70）

- **入口条件**：跨 crate 集成；
- **测试重点**：crate 间公开 API 契约、`Cargo.toml` 依赖方向、ABI 兼容；
- **工具**：workspace 级 `tests/` + 单独 integration crate；
- **通过标准**：所有跨 crate 测试通过 + `cargo tree` 仍满足 `AC-02`（核心 crate 不依赖 Graph / Vector / AI / 3DGS）。

### 11.14 障碍 / 不具合对应（74）

- **入口条件**：集成测试 / 系统测试发现缺陷；
- **流程**：同 §11.9 流程，外加**影响分析**（§11.32）。

### 11.15 功能测试（78）

- **入口条件**：MVP 所有 crate 完成 §65；
- **测试范围**：端到端功能场景——构建场景、运行 step、检查输出；
- **通过标准**：所有 `GVPE-FR-*` 与 `GVPE-AC-*` 至少 1 个端到端测试覆盖。

### 11.16 障碍测试（84）

- **测试输入**：
  - NaN / Inf 输入；
  - 零质量 / 负质量 / 极大质量；
  - 极大初速度 / 极大角速度；
  - 极端形状（退化 box、零半径 sphere）；
  - 极端重力；
  - 极端 timestep（0、负数、极大）；
  - 极端迭代次数（0、1、极大）；
- **期望行为**：返回错误码（FFI 边界），不 panic、不 UB、不死锁；
- **工具**：`proptest` 缩小 + `cargo-fuzz` 评估。

### 11.17 系统测试完成批准（89）

- **触发**：所有 ST 用例通过 + §84 障碍测试通过 + 性能预算达成（`GVPE-DOC-14`）；
- **批准人**：Release Manager + 架构师 + QA 负责人；
- **产出**：版本号 + release notes 草稿。

### 11.18 用户验收测试（92）

- **入口条件**：与至少 1 个集成方签署 UAT 协议；
- **流程**：集成方在自己的游戏项目中嵌入 GVPE MVP，跑真实场景，反馈结果；
- **通过标准**：集成方书面接受 + 无 Blocker bug。

### 11.19 业务场景测试（93）

- **测试范围**：集成方提供的真实业务场景（如 1000 刚体堆叠 / 关节驱动角色 / 高速运动物体 / 大规模破坏）；
- **通过标准**：性能达到集成方预期（具体数字由 UAT 协议规定）。

### 11.20 验收判定（94）

- **双方签字**：集成方代表 + GVPE Release Manager；
- **签字内容**：版本号、UAT 结果、已知 issue 列表、后续支持承诺。

### 11.21 验收（95）

- **合同流程**：依集成方与 GVPE 项目方的商务协议；
- **产出**：商务验收报告、付款 / 交付节点确认。

### 11.22 发布计划（102）

- **触发**：§89 系统测试完成批准后；
- **产出**：
  - semver 版本号（major / minor / patch）；
  - release notes（CHANGELOG.md）；
  - 兼容性声明（哪些下游集成方可能受影响）；
  - 发布时间窗口。

### 11.23 发布判定（103）

- **Go / No-Go 评审**：
  - 所有 ST 用例 ✅；
  - 所有 UAT 用例 ✅（如有）；
  - 性能预算达成；
  - 许可证审查通过（`cargo deny`）；
  - 安全公告无未处理 High；
  - 文档同步（无 doc drift）；
  - Release Manager 签字。

### 11.24 本番部署（105）

- **发布渠道**：
  - crates.io（`gvpe-*` 全套 crate）；
  - GitHub Release（带 `cdylib` / `staticlib` artifact）；
  - `gvpe-ffi` 的 C 头文件（由 `cbindgen` 生成）；
- **发布后**：
  - 通知集成方（按 §140 通信渠道）；
  - 更新 `docs/` 中"当前版本"指示。

### 11.25 稼动确认（106）

- **集成方 smoke**：集成方在新版本上跑最小场景确认无回归；
- **时间窗口**：发布后 48 小时内；
- **失败处理**：触发 §11.25.1（hotfix 评估）。

#### 11.25.1 发布失败应急

- **触发**：集成方 smoke 失败 / 自身监控发现严重问题；
- **动作**：评估 hotfix 必要性；如必要，进入 §11.37 hotfix 流程；如非必要，列入下一 patch。

### 11.26 初期流动对应（108）

- **时间窗口**：发布后 4 周；
- **重点**：集成方反馈快速响应（24 小时内首次响应）、紧急 bug 优先处理、性能调优；
- **结束标志**：集成方反馈频率稳定，发布版本进入稳态。

### 11.27 事件管理（114）

- **GitHub Issues 标签**：`incident`；
- **响应 SLA**：72 小时内首次响应（非严重）/ 24 小时（严重）；
- **关闭条件**：问题解决 + postmortem 文档（如适用）。

### 11.28 障害管理（115）

- **GitHub Issues 标签**：`bug`；
- **响应 SLA**：与 §114 类似，但所有 bug 必须有修复计划。

### 11.29 问题管理（116）

- **Postmortem 模板**：
  - 时间线（事件、检测、缓解、解决）；
  - 根因分析（5 Whys）；
  - 影响范围（哪些集成方、哪些版本）；
  - 改进措施（短期 + 长期）；
- **公开性**：除非涉及安全 / 客户隐私，否则 postmortem 公开（GitHub Wiki / blog）。

### 11.30 咨询管理（117）

- **渠道**：GitHub Discussions（提问 / 想法 / 公告 / 投票）；
- **响应 SLA**：1 周内首次响应。

### 11.31 变更要求（118）

- **入口**：集成方 / 内部 / 社区 / 法规触发；
- **形式**：GitHub Issue（标签 `change-request`）；
- **必填**：动机、影响范围、紧急度、提议方案。

### 11.32 变更管理（120 / 136）

- **影响分析**（§119）：用 `GVPE-DOC-27` §11 / §12 复审机制 + crate-level 影响分析；
- **决策**：架构师 + 维护者小组，Go / No-Go；
- **执行**：Go → 走 PR 流程；No-Go → 关闭 issue 并说明。

### 11.33 构成管理（121 / 137）

- **git tag 策略**：`vMAJOR.MINOR.PATCH`（semver）；
- **分支策略**：`main`（稳定）/ `develop`（集成）/ `feature/*`（功能）/ `release/*`（发布准备）/ `hotfix/*`（紧急）；
- **artifact**：crates.io + GitHub Release + cbindgen 头文件。

### 11.34 Patch 适用（122）

- **触发**：bug 修复（不影响 ABI / 公开 API 形状）；
- **流程**：常规 PR 流程；
- **发布**：semver patch（`v0.1.1`）。

### 11.35 脆弱性对应（123）

- **监控**：订阅 RUSTSEC 邮件列表 + GitHub Dependabot + `cargo audit`；
- **响应 SLA**：
  - Critical：48 小时 hotfix；
  - High：1 周内 patch；
  - Medium：下个 minor；
  - Low：backlog。
- **披露**：参照 GitHub Security Advisories 流程。

### 11.36 改修（124）

- **触发**：非紧急改进 / 新功能 / 性能优化；
- **流程**：常规 PR 流程；
- **发布**：semver minor（`v0.2.0`）或 major（`v1.0.0`，breaking change）。

### 11.37 紧急改修（125）

- **入口条件**：发布后严重问题（§11.25.1 触发）；
- **分支**：`hotfix/*` 从最新 release tag checkout；
- **流程**：最小修复 + 紧急 review + 紧急 release；
- **合并**：fix 回到 `main` + `develop`。

### 11.38 品质评审（128）

- **触发**：每个 minor / major release 前；
- **内容**：
  - 测试覆盖率报告（`cargo llvm-cov`）；
  - 性能 baseline 对比（criterion）；
  - 缺陷趋势（GitHub Issues 统计）；
  - `GVPE-DOC-27` QA 状态统计。
- **产出**：quality report（写入 `docs/quality/` 或 `docs/releases/`）。

### 11.39 品质评价（129）

- **指标**：
  - 单元测试覆盖率 ≥ 80% 行 / 70% 分支；
  - 性能回归 ≤ 5%；
  - 缺陷率（每 KLOC）< 历史均值；
  - `cargo deny` 0 violation；
  - `cargo clippy --all-targets` 0 warning（pedantic level）。
- **频率**：每个 release。

### 11.40 品质审计（130）

- **频率**：半年一次；
- **审计人**：架构师 + 1 名外部 reviewer（如有）；
- **内容**：
  - 文档完整性 / 一致性（28 份文档与代码同步）；
  - 流程执行记录（PR 流程、code review、release 流程）；
  - `GVPE-DOC-27` QA 状态；
  - 安全 / 许可证审查。
- **产出**：audit report + 改进行动清单。

### 11.41 WBS 管理（132）

- **分解粒度**：每个 crate = 一个 work package；crate 内每个模块 = 一个 work item；
- **跟踪**：GitHub Projects 或等价工具；
- **更新频率**：每周。

### 11.42 进度管理（133）

- **指标**：完成的 work item / 总 work item；
- **报告**：每周 / 每两周；
- **风险信号**：连续 2 周进度 < 80% 计划 → §134 课题登记。

### 11.43 变更管理（136）

- 见 §11.32（同 120）。

### 11.44 构成管理（137）

- 见 §11.33（同 121）。

### 11.45 评审管理（139）

- **评审类型**：
  - Design Review（基本 / 详细设计评审）；
  - Code Review（PR 评审）；
  - Release Review（Go/No-Go）；
  - Postmortem（事故复盘）。
- **跟踪**：每次评审产出纪要（commit / doc / issue comment）。

### 11.46 会议 / 报告（140）

- **定期会议**：
  - 周会：进度 + 风险同步；
  - 双周会：`GVPE-DOC-27` QA 状态审视；
  - 月会：性能 / 质量指标审视；
  - 季度会议：范围 / 战略审视。
- **报告**：周报 + 月报 + 季度报告。

### 11.47 工数管理（141）

- **记录**：每个 PR 关联 estimate（小时）与 actual；
- **回顾**：每月做一次 estimate vs actual 偏差分析；
- **工具**：GitHub Projects + 时间跟踪。

### 11.48 成本管理（142）

- **范围**：CI 时间、license 费、外部 reviewer 费、差旅（如有）；
- **跟踪**：季度审视；
- **优化机会**：CI 加速（`QA-T-05`）、license 选择。

### 11.49 项目完成判定（145）

- **触发**：MVP / Phase N 目标全部达成 + §89 / §94 通过；
- **判定人**：项目负责人 + 架构师 + 关键集成方代表（如适用）；
- **产出**：项目完成报告。

### 11.50 成果物交接（146）

- **交接内容**：
  - 文档全集（`docs/00` ~ `docs/28` + archive）；
  - crate 集合（crates.io + GitHub Release）；
  - C 头文件集；
  - CI / 工具链配置；
  - 维护期 contact。
- **交接对象**：维护团队 / 集成方。

### 11.51 完成报告（147）

- **内容**：
  - 项目目标达成度（按 §143 范围管理核对）；
  - 关键指标（性能 / 质量 / 工数 / 成本 vs 计划）；
  - 重大变更（按 §136 变更管理记录）；
  - 经验教训（按 §148 回顾）；
  - 后续建议。

### 11.52 回顾（148）

- **格式**：KPT（Keep / Problem / Try）；
- **参与者**：核心团队全员；
- **产出**：retro 文档，写入 `docs/retros/`；
- **行动项**：转化为 `GVPE-DOC-27` QA 项（如有需要）。

### 11.53 知识移交（149）

- **对象**：新加入成员 / 接手维护者；
- **内容**：
  - 文档全集（重点是 `00` / `01` / `17` / `26` / `27` / `28`）；
  - 架构 tour（口头 + 屏幕共享）；

  - 已知坑（`GVPE-DOC-27` 中 High / Blocker 项 + 集成方常见问题）。
