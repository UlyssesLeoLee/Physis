## 2. 文档目的

本文档规定 `gvpe-graph` / `gvpe-vector` 选用嵌入式 Graph / Vector 数据库时的许可证审查矩阵。目标：

- 把许可证风险当作与架构风险同等的“硬门禁”而非评分项——任何一项不通过即拒绝。
- 与 `GVPE-PROHIBIT` 列表的硬门禁模式保持一致。
- 给出明确的回退位置：若外部候选无一通过审查，则回退到手写嵌入式存储。

## 3. 适用范围

- 适用：作为 `gvpe-graph` / `gvpe-vector` 后端的候选 Graph / Vector 数据库。
- 不适用：`gvpe-core` / `gvpe-solver` 等的普通 Rust crate 依赖（数学、SIMD、线程库等）——它们走常规 OSS 许可证卫生流程，但不走本次重量级审查；本次审查存在的原因正是“嵌入 DB 引擎”涉及商业再分发利益，而数学 crate 不涉及。

## 4. 术语定义

| 术语 | 说明 |
|---|---|
| OSI 批准 | Open Source Initiative 认可的许可证 |
| 宽松许可证 | 允许商业使用、改动、再分发的最小限制型许可证 |
| 弱 copyleft | 在改动作品本身时要求开源，但允许以动态 / 静态链接形式与闭源软件共存 |
| OEM | GVPE 作为更大产品的嵌入式组件被转售 |
| 静态链接 / 动态链接 | 将第三方库以何种方式合入最终二进制 |
| AGPL 网络使用条款 | 部分 AGPL 变体要求通过网络提供服务时也开放源码 |
| 嵌入式 / 库形态 | 作为库随主程序一同发布，而不是作为独立服务部署 |
| 后备选项 | 当所有外部候选审查失败时，项目自有的实现（手写嵌入式存储） |
| 重新审查触发 | 已选依赖的许可证发生变更（重大版本升级、重新许可证）的事件 |

## 5. 前提与约束

- 满足 `GVPE-LIC-001`：所有候选 Graph / Vector 后端必须通过 §6.2 矩阵。
- 矩阵中任何一栏不通过即拒绝——这是硬门禁，不是带权打分。
- 已选依赖的许可证一旦变更，必须立即按 §6.2 重新审查。
- 03_graph_schema.md §1.A 中的后端选型尚未敲定；本文档的审查矩阵先行就位。

## 6. 系统架构 / 模块设计

### 6.1 范围

本文审查矩阵适用于任何作为 `gvpe-graph` / `gvpe-vector` 后端的候选 Graph / Vector 数据库。不适用于 `gvpe-core` / `gvpe-solver` 等的普通 Rust crate 依赖（数学、SIMD、线程库等）——它们遵循常规 OSS 许可证卫生流程，但不走本次重量级审查；本次审查存在的原因正是“嵌入 DB 引擎”涉及商业再分发利益，而数学 crate 不涉及。

### 6.2 审查矩阵（每个候选在选定前必须通过全部条目）

| 检查项 | 问题 | 通过标准 |
|---|---|---|
| 许可证 | 什么许可证？ | OSI 批准；宽松或弱 copyleft，且与商业再分发兼容 |
| 商业使用 | 明确允许？ | 是，且无歧义地写于许可证文本本身 |
| OEM | GVPE 能否被作为更大产品的一部分嵌入并转售？ | 是 |
| 再分发 | 编译产物能否再分发？ | 是，且不要求按份付费或注册 |
| 修改 | 源码能否被修改并以修改版发布？ | 是 |
| 静态链接 | 是否允许？ | 是，且不会让 GVPE 自身代码承担 copyleft 义务 |
| 动态链接 | 是否允许？ | 是 |
| SaaS | 若以托管服务形式提供，是否触发 AGPL 类网络使用条款？ | 不存在该条款，或该条款对项目可接受 |
| 嵌入式使用 | 明确支持嵌入式 / 库形态（非仅独立服务端部署）？ | 是 |

候选在任何一行上失败即被直接拒绝——这是硬门禁而非评分权衡（沿用 `01_requirements.md` 中 `GVPE-PROHIBIT` 列表对架构约束的非协商门禁模式；许可证风险在此被赋予与架构风险同等的处理）。

### 6.3 候选追踪（随 spike 推进而填——不做预选）

| 手写嵌入式 Vector 索引 / `usearch` 类库 | Vector | TBD | 尚未审查 |
| 任意完整 Graph DB 引擎（如可嵌入式 graph 库） | Graph | TBD | 尚未审查 |

上表中的任何一行都不是承诺——本表存在的意义，是让 spike 真正发生后审查的“输出”可被审计，而不是提前宣告决策。

## 7. 接口设计

| 方向 | 接口 | 用途 |

## 9. 处理流程

1. 列出候选（手写 / 外部库）。
2. 对每个外部候选逐项核对 §6.2。
3. 任一候选任一行失败即拒绝。
4. 全部外部候选拒绝 → 启用 §6.4 回退位置。
5. 已选依赖一旦发生许可证变更，立即按 §6.5 重新审查。

### 13.4 回退位置

若 Graph 或 Vector 存储均无外部候选通过 §13.2，则 `gvpe-graph` / `gvpe-vector` 默认回退到手写嵌入式存储（自有许可证，必然合规）。这是可接受的结果而非失败状态——`03_graph_schema.md` §6 中的查询模式（有限遍历、无界多跳被有意规避）正是为了让手写存储在第三方候选失败时仍可行。

### 13.5 重新审查触发

任何已选依赖的许可证变更（新主版本、重新许可证）立即触发按 §13.2 的重新审查，不享受“祖父条款”豁免。
